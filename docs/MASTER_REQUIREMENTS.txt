9. CALCULATIONS AND ACCOUNTING INTEGRITY

Authoritative posting calculations execute in Supabase PostgreSQL within the protected transaction. Express validates inputs and invokes the relevant RPC. Frontend previews must match the database rules and never become the source of truth.

Distance = end odometer - start odometer.
Fuel efficiency = valid distance / corresponding consumed fuel litres.
Trip expenses = the sum of that trip's approved expense lines.
Trip operating profit = approved fare - approved trip expenses.
Loan balance = opening principal + disbursements - repayments, adjusted only through audited correction entries.

Never reverse the distance subtraction or label litres/km as km/L.

Validate end odometer >= start odometer. Handle an actual odometer replacement/reset through a separate audited adjustment. Missing or zero litres produce Not available, not Infinity, NaN, or a misleading zero efficiency.

Fuel purchased is not necessarily fuel consumed. Support a measurement basis: measured consumption, tank-reconciled consumption, or purchase-based estimate. Label estimates honestly. Do not mix incompatible bases in a supposedly measured ranking.

Pooled fuel efficiency = sum of eligible distances / sum of the corresponding eligible litres. Exclude unmatched incomplete records from both sides. Never average individual trip efficiency ratios without weighting.

Use PostgreSQL NUMERIC(18,2) for monetary amounts, explicit precision for fuel/distance/weight, and documented decimal-safe rounding. Serialize money safely as decimal strings and use a decimal-safe library for any JavaScript arithmetic. Do not coerce financial totals into unrestricted binary floating-point arithmetic. Allow negative profit, but validate negative charges through explicit refund/adjustment workflows.

Create canonical revenue and expense records linked to source documents. Each source line must post only once. A repair entered through Maintenance and linked to a trip is one expense, not two. An oil change's financial charge must not be counted again in maintenance totals.

Separate earnings/expenses from cash receipts/payments. Loan principal, repayments, salary advances, and settling previously accrued commission must not create duplicate operating income or expenses. Track receivables, payables, and settlement allocations where needed.

Separate opening balances and historical cumulative maintenance figures from current-period expenses. Vehicle acquisition costs and owner distributions must not silently become ordinary trip expenses.

Call the default result Operating Profit. Do not imply a statutory, tax, or audited net-profit calculation where depreciation, taxes, or other adjustments are not configured.

Implement coordinated financial changes in a single PostgreSQL function call/transaction with appropriate row locking, constraints, unique source-line indexes, optimistic concurrency, and idempotency keys. A sequence of separate Supabase HTTP calls is not an atomic transaction.

For actions such as approve_trip, approve_expense, issue_driver_loan, record_driver_repayment, settle_driver_payment, close_period, and reopen_period, validate permissions and perform all related updates plus the audit event together. Fail and roll back completely on invalid input, insufficient rights, a closed period, or a conflict. Never swallow an exception and report a partial posting as successful.

Use a consistent lock order between posting and period closing. Protect state transitions and approved values at database level so direct table updates cannot bypass them. SQL SECURITY INVOKER is the default; use a narrowly scoped SECURITY DEFINER function only where needed to access protected posting tables, with explicit caller checks, restricted EXECUTE grants, a safe search_path, fully qualified object names, and no arbitrary SQL execution.

Include reconciliation queries and reports. PostgreSQL transactions cannot roll back external Auth or Storage HTTP operations: use pending states, idempotency, compensation, and cleanup for these cross-service workflows rather than pretending they are one atomic transaction.
